# Apple Pi GitHub 展示重构设计规格（v1.4.4）

## 目标与受众

本次工作要重做 Apple Pi GitHub README 顶部的演示 GIF、完整界面截图与产品介绍。读者是正在比较桌面 Agent、代码 Agent、CLI Agent 或模型聊天工具的 Windows 开发者。他们在 GitHub 上只有数十秒判断时间，因此首屏不能再是空白欢迎页，也不能只展示一个看起来会动但没有因果关系的镜头。读者需要先看懂：这是一套怎样的真实桌面工作区、用户如何把一个任务放进去、计划如何被看见和确认、以及它为什么比常见的“一个聊天框加工具按钮”的 Agent 体验更适合持续开发。

## 必须传达的内容

1. **完整工作区，而不是局部截屏。** 截图必须保留应用窗口的四个共同上下文：任务侧栏、对话主区、底部输入与权限/计划策略控制、计划列表。所有展示图采用隔离 Electron 实例，不出现用户项目、磁盘路径、账户或凭证。
2. **一条可以复述的演示过程。** GIF 应严格讲一个单一因果链：「提出任务」→「生成结构化计划」→「等待确认」→「进入可控执行」。每一镜只强调一个行为；完整窗口用于定场，局部特写只用于讲清计划和权限，而不是替代完整界面。
3. **Apple Pi 的可验证优势。** 介绍区将以“Apple Pi / 一般桌面 Agent 的常见形态”对比表表达：项目与会话归档、独立计划策略与执行权限、计划优先且可仅规划、模型和本地运行时选择、Git/浏览器/终端工作台、MCP 与 Skill 的导入和开关。这些是项目 README 与现有界面直接可见的能力；文字不使用“所有竞品都没有”一类绝对表述。
4. **从产品自身长出的视觉语言。** 使用 Apple Pi 现有的白底、墨蓝和细边框作为母语；点缀色只服务于“计划/确认”这一条叙事线。展示页采用高可读中文排版，标题使用有分量的宋体/系统衬线，正文遵循桌面 UI 的清晰无衬线风格。避免 GitHub 深蓝霓虹、装饰性指标、emoji 图标和无意义渐变。

## 输出与约束

- 最终 README 需要：一个 16:9、约 15–18 秒、清楚分镜的 GIF（同时保留 MP4）；至少两张真实 16:9 完整窗口截图；一段更完整的产品说明；一张中文对比表。
- GIF 的镜头以真实 2x UI 截图为底，采用“截图运镜 + 少量真实切片/标注”的混合路径。光标、标注与行动顺序必须一直在 8% 安全边距内；不重建不存在的界面。
- 片长小于 20 秒，但仍须先完成轻量分镜卡。最终以全景、静止的完整窗口收尾，不能在放大的局部截然而止。
- 三份方向板使用同一份真实完整窗口截图。差异必须是镜头叙事、信息层级和 README 首屏结构，而不是把同一布局换三套颜色。

## 方向板判定标准

选择时重点看四件事：第一眼是否能看出是 Apple Pi 而不是通用 AI 页面；是否明确看懂“任务—计划—执行”的过程；是否完整看到桌面应用，而非一块漂浮的局部面板；是否能自然容纳较完整的优势介绍和对比表。确认方向后，才会输出最终 GIF、完整截图组和 README 文案，并将选择原话、分镜、产出路径写入 `direction-approved.md`。
