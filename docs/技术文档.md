## 1. 项目概述

Pi 是一个开源的极简终端 Coding Agent（monorepo：`github.com/earendil-works/pi`），其核心理念是 **"让工具适应你的工作流，而不是反过来"**。它采用严格的分层架构，把"LLM 接入"、"Agent 循环"、"终端应用"拆成三个独立 npm 包，方便开发者按需引用、构建自己的 Agent 软件：

| 包 | 定位 | 一句话说明 |
|---|---|---|
| `@earendil-works/pi-ai` | LLM 接入层 | 统一多家 LLM Provider 的 API，自动模型发现与鉴权 |
| `@earendil-works/pi-agent-core` | Agent 运行时 | 有状态 Agent：工具调用、事件流、状态管理、消息队列 |
| `@earendil-works/pi-coding-agent` | 应用层 | `pi` CLI：read/bash/edit/write 工具 + 会话管理 + TUI |
| `@earendil-works/pi-tui` | UI 层（附属） | 终端 UI 组件库（被 coding-agent 依赖） |

设计哲学要点：

- **极简内核**：CLI 默认只给模型 `read`、`write`、`edit`、`bash` 四个工具（内置另有 `grep`、`find`、`ls`）。
- **不内置重功能**：sub-agent、plan mode、权限弹窗、TODO、后台 bash 等均**不内置**，通过扩展生态按需添加。
- **No MCP**：官方不内置 MCP 协议，以 Skills / CLI 工具 / 扩展机制替代（扩展层可自行接入 MCP）。
- **Tree-shaking 友好**：pi-ai 核心入口不引入任何 provider SDK，按需加载。

### 2.2 依赖关系

三包为**严格单向分层**，无循环依赖：

```
pi-coding-agent ──► pi-agent-core ──► pi-ai ──► 各 provider SDK
       │
       └──────► pi-tui（终端 UI 组件）
```

- `pi-ai` 不依赖其他两个包，可单独作为多 Provider LLM SDK 使用；
- `pi-agent-core` 依赖 `pi-ai`，可单独作为通用 Agent 运行时嵌入任意应用（不限于编码场景）；
- `pi-coding-agent` 同时依赖两者 + `pi-tui`，是完整的终端应用。

### 2.3 数据流总览（一次 prompt 的完整生命周期）

```
用户输入 prompt
   │
   ▼
[应用层] 编辑器 → prompt(text, images?)                    (pi-coding-agent)
   │
   ▼
[运行时] Agent.prompt() → agent_start 事件                  (pi-agent-core)
   │   AgentMessage[] → transformContext() → convertToLlm() → Message[]
   ▼
[接入层] models.stream(model, context)                      (pi-ai)
   │   统一流式事件: text_delta / thinking_delta / toolcall_delta …
   ▼
[运行时] message_update 事件冒泡 → UI 渲染流式输出
   │   message_end(assistant) → 若有 toolCall → 参数校验 → 执行工具
   │   tool_execution_start/update/end → toolResult 消息入上下文
   ▼
循环：直到 assistant 消息无工具调用 → turn_end → agent_end
   │
   ▼
[应用层] 会话条目(id+parentId) 追加写入 JSONL 会话文件
```

## 4. 分层详解

### 4.1 pi-ai：统一多 Provider LLM API

> 定位：把 30+ 家 LLM 的差异化 API 收敛为一套统一接口。**只收录支持工具调用（function calling）的模型**，因为工具调用对 agentic 工作流至关重要。

#### 4.1.1 核心抽象

- **Provider**：运行时单元。每个 Provider 拥有自己的模型目录、鉴权逻辑（API Key 解析 / OAuth 流程）与流式行为。
- **`Models` 集合**：持有多个 Provider，把每个请求路由到"拥有该模型"的 Provider。
- **API 实现（wire 协议）被 Provider 内部共享**，包括：
  `anthropic-messages`、`openai-responses`、`openai-completions`（xAI/Groq/Cerebras/OpenRouter 等共用）、`openai-codex-responses`、`azure-openai-responses`、`google-generative-ai`、`google-vertex`、`mistral-conversations`、`bedrock-converse-stream`。混合 API Provider（GitHub Copilot、OpenCode Zen）按模型分发。
- **Tree-shaking**：核心入口不引入任何 Provider/SDK；`providers/<name>` 子路径按需引入；`providers/all` 全量引入；`api/<api-id>.lazy` 包装器把 SDK 延迟到首次请求时才加载。

#### 4.1.2 支持的 Provider（30+）

OpenAI、Ant Ling、Azure OpenAI (Responses)、OpenAI Codex（ChatGPT Plus/Pro 订阅，OAuth）、DeepSeek、NVIDIA NIM、Anthropic、Google、Vertex AI、Mistral、Groq、Cerebras、Cloudflare AI Gateway、Cloudflare Workers AI、xAI、OpenRouter、Vercel AI Gateway、ZAI Coding Plan（Global/China）、MiniMax（Global/China）、Together AI、Hugging Face、Moonshot AI（含 China）、GitHub Copilot（OAuth）、Amazon Bedrock、OpenCode Zen、OpenCode Go、Fireworks、Kimi For Coding（Moonshot 订阅端点，Anthropic 兼容 API）、Xiaomi MiMo（API 计费 + cn/ams/sgp 三区 Token Plan），以及**任意 OpenAI 兼容 API**（Ollama、vLLM、LM Studio 等）。

#### 4.1.3 四个核心方法

| 方法 | 用途 |
|---|---|
| `models.stream()` | 全事件流式调用 |
| `models.complete()` | 一次性获取完整响应 |
| `models.streamSimple()` | 简化流式（统一 thinking 选项） |
| `models.completeSimple()` | 简化一次性（统一 thinking 选项） |

#### 4.1.4 统一流式事件模型

```
start → [text_start → text_delta* → text_end]
      → [thinking_start → thinking_delta* → thinking_end]
      → [toolcall_start → toolcall_delta* → toolcall_end]   // 参数为 partial JSON 增量
      → done (reason: stop | length | toolUse)
      → error (error | aborted)
```

- 事件按 `contentIndex` 关联内容块，块间事件可交错；
- 工具参数以 partial JSON 增量解析，UI 可渐进式展示参数；
- **流函数从不抛出异常**：错误以 error 事件 + `stopReason: "error"/"aborted"` 的最终消息呈现，部分内容与 token 用量保留；中止后的消息可放回上下文继续对话。

#### 4.1.5 鉴权体系

- 每个 Provider 自行解析凭证，优先级：**显式 `apiKey` > 存储凭证 > 环境变量 > 环境感知源**（AWS profile、gcloud ADC 等）；
- **`CredentialStore` 接口**（`read/list/modify/delete`），OAuth token 刷新在 `modify` 内串行化，防止并发重复刷新；默认内存实现，可注入持久化存储；
- `models.getAuth()` 可不发请求检查鉴权状态；
- `transformHeaders` 在派发前最终修改请求头（顺序：provider auth → model.headers → options.headers → transformHeaders）；
- OAuth 交互式登录：`models.login(providerId, 'oauth', interaction)`（Anthropic Claude Pro/Max、OpenAI Codex、GitHub Copilot）。

#### 4.1.6 Thinking / Reasoning 统一抽象

- 统一级别：`off | minimal | low | medium | high | xhigh | max`（`xhigh`/`max` 为模型特定 opt-in，`getSupportedThinkingLevels()` 查询）；
- 同时支持 Provider 原生选项：Anthropic `thinkingBudgetTokens`、OpenAI `reasoningEffort`、Google `thinking.budgetTokens`；
- 模型可用 `thinkingLevelMap` 自定义级别映射。

#### 4.1.7 跨 Provider Handoff（会话中途换模型）

- 同一个 `Context` 可在 Claude → GPT → Gemini 之间无缝切换；
- 异源 assistant 消息的 thinking 块自动转成 `<thinking>` 标签文本；
- tool call、图片、被中止的部分内容均可传递。

#### 4.1.8 自定义 Provider

```typescript
createProvider({
  id, auth, models, api,
  fetchModels?  // 动态模型列表
})
```

- 可挂自定义 `baseUrl`、模型级 `headers`、`compat` 兼容标志（`supportsDeveloperRole`、`supportsReasoningEffort`、`maxTokensField`、`thinkingFormat` 等大量 OpenAI 兼容差异开关）；
- 动态模型列表：`fetchModels` + `models.refresh()` + `ModelsStore` 持久化；
- `fauxProvider()`：脚本化假 Provider，用于测试。

#### 4.1.9 其他

- 图像生成走独立表面 `ImagesModels` / `generateImages()`；
- `Context` 与 `Model` 均为纯 JSON 可序列化（便于持久化与传输）；
- 浏览器可用（Bedrock 与 OAuth 登录为 Node-only）。

### 4.2 pi-agent-core：Agent 运行时

> 定位：构建于 pi-ai 之上的**有状态 Agent**——工具执行、事件流、状态管理、消息队列。通用运行时，不限于编码场景。

#### 4.2.1 消息模型：AgentMessage vs LLM Message

- `AgentMessage` 是运行时消息，可通过 TypeScript **declaration merging** 扩展自定义消息类型（如 `notification`）；
- 每次 LLM 调用前的转换管线：

```
AgentMessage[] → transformContext()（可选：裁剪/注入/压缩）
              → convertToLlm()（必需：过滤/转换为 LLM Message）
              → Message[] → LLM
```

#### 4.2.2 事件流（状态管理核心）

一次 `prompt("Hello")` 的典型事件序列：

```
agent_start
 └─ turn_start
     ├─ message_start / message_end (user)
     ├─ message_start (assistant)
     │    └─ message_update* (流式 delta，含 assistantMessageEvent)
     ├─ message_end (assistant)
     ├─ tool_execution_start / update* / end      // 若有工具调用
     ├─ message_start / message_end (toolResult)  // 若有工具调用
     └─ turn_end
agent_end
```

完整事件类型表：

| 事件 | 说明 |
|---|---|
| `agent_start` / `agent_end` | Agent 运行开始/结束 |
| `turn_start` / `turn_end` | 单轮开始/结束（工具调用后自动开启下一 turn，直到无工具调用） |
| `message_start` / `message_end` | 消息边界 |
| `message_update` | 仅 assistant，流式 delta |
| `tool_execution_start` / `tool_execution_update` / `tool_execution_end` | 工具执行及流式进度 |

**关键语义**：

- `subscribe(fn)` 监听器按注册顺序 await；
- `prompt()` / `waitForIdle()` 只有在 `agent_end` 监听器全部完成后才 settle（`isStreaming` 也到那时才变 false）；
- `Agent` 类把 assistant `message_end` 处理作为工具 preflight 前的屏障（barrier）；低层 `agentLoop()` 流是"观察性"的，不等待异步处理。

#### 4.2.3 Agent 状态

```typescript
interface AgentState {
  systemPrompt: string;
  model: Model<any>;
  thinkingLevel: ThinkingLevel;
  tools: AgentTool<any>[];
  messages: AgentMessage[];
  readonly isStreaming: boolean;
  readonly streamingMessage?: AgentMessage;
  readonly pendingToolCalls: ReadonlySet<string>;
  readonly errorMessage?: string;
}
```

- 可直接赋值修改（`state.tools`、`state.messages` 赋值时复制顶层数组）；
- `agent.reset()` 重置。

#### 4.2.4 核心方法

| 方法 | 说明 |
|---|---|
| `prompt(text \| AgentMessage, images?)` | 发送用户消息并驱动完整循环 |
| `continue()` | 从现有上下文恢复（最后一条必须是 user 或 toolResult），用于错误重试 |
| `abort()` | 中止当前运行 |
| `waitForIdle()` | 等待进入空闲态 |
| `subscribe(fn)` | 订阅事件，返回 unsubscribe |
| `steer(msg)` | **Steering**：工具运行期间打断，当前 turn 结束后注入 |
| `followUp(msg)` | **Follow-up**：agent 将停止时排队追加工作 |
| `clearSteeringQueue()` / `clearFollowUpQueue()` / `clearAllQueues()` | 队列清理（两种队列各有 `one-at-a-time`（默认）/`all` 模式） |

#### 4.2.5 工具系统（AgentTool）

```typescript
const tool: AgentTool = {
  name: "my_tool",
  label: "My Tool",
  description: "...",
  parameters: Type.Object({...}),            // TypeBox schema
  executionMode: "sequential" | "parallel",  // 可选，覆盖全局默认
  execute: async (toolCallId, params, signal, onUpdate) => {
    onUpdate?.(partialResult);               // 可选：流式进度
    return {
      content: [{ type: "text", text: "..." }],
      details: {...},                        // 结构化详情（UI 展示用）
      terminate: true                        // 可选：整批全部 terminate 时跳过自动后续 LLM 调用
    };
  }
};
```

**执行模式**：

- 全局 `toolExecution: "parallel"`（默认）| `"sequential"`；
- preflight（校验+钩子）顺序执行，允许的工具并发执行；
- 批中任一工具声明 `executionMode: "sequential"` 则整批顺序执行；
- 事件按完成顺序发出；持久化的 toolResult 按 assistant 源顺序排列。

**钩子**：

- `beforeToolCall({toolCall, args, context})`：参数校验后执行，可 `{block: true, reason}` 阻止执行（权限门的实现点）；
- `afterToolCall({toolCall, result, isError, context})`：最终事件前可改写 `details` 或返回 `terminate: true`。

**错误处理约定**：工具失败必须 **throw**（不要把错误文本作为 content 返回）；Agent 捕获后以 `isError: true` 的 toolResult 报告给 LLM。

#### 4.2.6 其他能力

- `sessionId`：Provider 缓存亲和（提升 prompt cache 命中率）；
- `getApiKey`：动态解析过期 OAuth token；
- `thinkingBudgets`：自定义各 thinking 级别的 token 预算；
- `streamProxy`：浏览器场景走后端代理；
- 低层 API `agentLoop()` / `agentLoopContinue()`：完全脱离 `Agent` 类手工驱动循环；可传 `shouldStopAfterTurn` 在当前 turn 正常完成后优雅停止（不中止流、不取消工具）。

### 4.3 pi-coding-agent：CLI/TUI 应用层

> 定位：完整的终端 Coding Agent 应用（`pi` 命令，bin 入口 `dist/cli.js`），也是**最好的 SDK 参考实现**。

#### 4.3.1 四种运行模式

| 模式 | 入口 | 适用场景 |
|---|---|---|
| Interactive (TUI) | `pi` | 人机交互 |
| Print / JSON | `pi -p` / `pi --mode json` | 脚本管道、CI；print 模式可读 stdin 合并进 prompt |
| RPC | `pi --mode rpc` | stdin/stdout 上 LF 分隔的 JSONL，供**非 Node 进程**集成 |
| SDK | `createAgentSession` 等 | 嵌入你自己的 Node/TS 应用 |

#### 4.3.2 内置工具

`read`、`write`、`edit`、`bash`（默认四个）+ `grep`、`find`、`ls`。

CLI 工具控制参数：`--tools/-t`、`--exclude-tools/-xt`、`--no-builtin-tools/-nbt`、`--no-tools/-nt`。

#### 4.3.3 交互界面（TUI）

- **启动头**：快捷键 / 已加载 AGENTS.md / 模板 / skills / 扩展一览；
- **消息区**：对话与工具输出渲染；
- **编辑器**：边框颜色指示 thinking 级别；`@` 模糊引用项目文件、Tab 路径补全、Shift+Enter 多行、Ctrl+G 外部编辑器（`$VISUAL`/`$EDITOR`）、Ctrl+V 粘贴图片/文本、`!cmd` 执行命令并把输出送给 LLM（`!!cmd` 不发送）；
- **底栏**：cwd、会话名、token/缓存用量、成本、上下文占用、当前模型。

## 5. 关键机制深入

### 5.1 工具调用的完整链路

```
LLM 流式输出 toolcall_delta (partial JSON)
   → pi-ai 增量解析 → toolcall_end（完整参数）
   → pi-agent-core: TypeBox 参数校验（validateToolCall）
   → beforeToolCall 钩子（可 block）
   → execute(toolCallId, params, signal, onUpdate)
        ├─ onUpdate(partialResult) → tool_execution_update 事件（流式进度）
        └─ 返回 / throw
   → afterToolCall 钩子（可改写 details / terminate）
   → tool_execution_end 事件
   → toolResult 消息（按 assistant 源顺序）写入上下文
   → 若批中无 terminate → 自动开启下一 turn（继续调 LLM）
```

### 5.2 Steering / Follow-up 消息队列

- **Steering**：在工具执行期间输入的消息，当前 turn 结束后注入上下文——用于"打断正在跑的 agent 并修正方向"；
- **Follow-up**：在 agent 即将停止时追加的排队工作——用于"做完这个再做那个"；
- 两种队列均支持 `one-at-a-time`（默认）与 `all` 两种投递模式；
- TUI 中对应 Enter（steering）/ Alt+Enter（follow-up）/ Alt+Up（取回）。

### 5.3 会话树与 Compaction

- JSONL 每行一个条目：`{id, parentId, ...}`，天然构成树，支持分支/回跳（`/tree`、`/fork`）；
- Compaction 是对 LLM 可见上下文的**有损压缩**（通过 `transformContext` 管线实现），完整历史不丢失，可随时回看。

### 5.4 缓存与成本

- `sessionId` 提供 Provider 缓存亲和；
- `PI_CACHE_RETENTION=long`：Anthropic 1 小时 / OpenAI 24 小时缓存；
- pi-ai 内置 token / 成本追踪，TUI 底栏实时展示。

### 5.5 错误与中止哲学

- 流式 API **从不 throw**：错误 = error 事件 + `stopReason: "error"/"aborted"`，部分内容与 usage 保留；
- 工具失败必须 throw，由运行时转为 `isError: true` 的 toolResult 反馈给 LLM（让模型自我修正）；
- 被中止的消息可放回上下文，`continue()` 无缝续跑。

## 7. 桌面端总体架构（方案 A：Electron + SDK 直嵌）

> 本章是"类 Codex 桌面端 Agent"的落地架构。选择 **Electron + pi SDK 直嵌**：Node 生态无缝、密钥不出主进程、调试简单，是桌面 Agent 的事实标准（VS Code 同款技术栈）。

### 7.1 架构图

```
┌─────────────────────────── Electron 窗口 ───────────────────────────┐
│                                                                      │
│  渲染进程（HTML/CSS/JS，后续可换 React/Vue）                          │
│   对话气泡 │ thinking 折叠块 │ 工具卡片 │ 状态栏 │ 输入框              │
│   （后续：diff 视图 │ 文件树 │ 审批弹窗 │ 会话列表 │ 模型选择器）       │
│─────────────────────── IPC (contextBridge) ─────────────────────────│
│  preload.cjs：暴露最小受控 API (window.piAgent)                       │
│─────────────────────── IPC (ipcMain.handle) ────────────────────────│
│  主进程（Node.js）                                                   │
│   AgentService（agent-service.js）                                   │
│   ├── createAgentSession()  ← @earendil-works/pi-coding-agent        │
│   ├── session.subscribe(event ⇒ IPC 广播到渲染进程)                   │
│   ├── prompt / abort / continue / 模型切换                            │
│   └── 预留 beforeToolCall 审批钩子（高危操作弹窗确认）                 │
│   ↓ SDK 内部                                                         │
│   ├── pi-coding-agent（会话/内置工具 read,bash,edit,write,grep,find,ls）│
│   ├── pi-agent-core（Agent 循环 + 10 类事件流 + Steering/Follow-up）  │
│   └── pi-ai（30+ Provider 接入 + 密钥/OAuth，密钥不出主进程）          │
└──────────────────────────────────────────────────────────────────────┘
```

### 7.2 进程职责与安全边界

| 进程 | 职责 | 能访问 | 不能访问 |
|---|---|---|---|
| **渲染进程** | UI 渲染、用户交互 | `window.piAgent`（preload 暴露的白名单 API） | Node API、文件系统、**API Key** |
| **主进程** | Agent 会话、工具执行、密钥、IPC | Node 全部能力、pi SDK、凭证 | —（受信任域） |

安全要点：

- `contextIsolation: true`、`nodeIntegration: false`：渲染进程无法直接 `require`；
- preload 用 `contextBridge.exposeInMainWorld` 只暴露必要方法，事件用 `ipcRenderer.on` 订阅；
- **API Key / OAuth token 只存在于主进程**，渲染进程永远接触不到——这是相对纯 Web 架构的核心安全优势；
- 高危工具（bash 写操作等）经 `beforeToolCall` 钩子在主进程拦截，弹窗由渲染进程呈现、用户决策回传主进程放行/阻断。

### 7.3 SDK 嵌入关键代码（主进程）

```javascript
import { createAgentSession, ModelRuntime, SessionManager }
  from "@earendil-works/pi-coding-agent";

const modelRuntime = await ModelRuntime.create();
const { session } = await createAgentSession({
  modelRuntime,
  sessionManager: SessionManager.inMemory(),  // 或文件会话 SessionManager.create(cwd)
  cwd,
  // 不传 tools ⇒ 默认启用内置 read/bash/edit/write（+grep/find/ls）
  // tools: ["read","bash"],   // 仅启用指定工具（工具名字符串数组）
  // customTools: [...],        // 自定义工具对象数组（TypeBox schema）
  // beforeToolCall: async ({toolCall, args}) => approved ? {} : {block:true, reason}
});

// 订阅事件流 → 转发渲染进程
session.subscribe((event) => win.webContents.send("agent:event", event));

await session.prompt("修复 login.ts 的类型错误");
```

### 7.4 渲染进程事件解析（已按真实事件结构校准）

pi-agent-core 推送的事件经实测（DeepSeek 模型）字段结构如下，渲染进程据此渲染：

| 事件 type | 关键字段 | 渲染动作 |
|---|---|---|
| `message_update` | `assistantMessageEvent: { type:"text_delta", delta }` | 追加到当前 assistant 气泡 |
| `message_update` | `assistantMessageEvent: { type:"thinking_delta", delta }` | 追加到 thinking 折叠块 |
| `message_end` | `message.role === "assistant"` | 结束当前气泡 |
| `tool_execution_start` | `{ toolCallId, toolName, args }` | 新建工具卡片（running），展示 `args` |
| `message_end` | `message.role === "toolResult"`：`{ toolCallId, toolName, content, isError }` | 更新对应工具卡片为 done/error 并填结果 |
| `agent_end` | — | 收尾，恢复输入可用 |

> ⚠️ 注意：`tool_execution_start` 的参数字段是 **`args`**（不是 `toolCall.arguments`）；`toolResult` 的标识字段是 `toolCallId`/`toolName`。这些已与 0.81.1 实测一致。

### 10.4 踩坑记录（重要）

1. **`createAgentSession` 的 `tools` 是工具名字符串数组**（如 `["read","bash"]`），**不是**工具对象数组；不传则默认启用内置 read/bash/edit/write。误传 `createCodingTools()` 的对象会导致"Available tools: (none)"。自定义工具对象走 **`customTools`**。
2. **`tool_execution_start` 事件字段是 `args`**（不是 `toolCall.arguments`）；`toolResult` 用 `toolCallId`/`toolName`/`content`/`isError`。
3. Electron 二进制需单独下载，国内务必设 `ELECTRON_MIRROR`，否则 postinstall 静默失败（`dist/electron.exe` 缺失报 ENOENT）。

## 11. 安全与合规

| 项 | 说明 |
|---|---|
| 许可证 | MIT（三包一致），可商用 |
| 扩展安全 | Extensions / Pi Packages 拥有**完全系统访问权**，安装第三方包需审计 |
| 项目信任 | `defaultProjectTrust`（ask/always/never）机制，未信任项目不加载其扩展 |
| 权限控制 | 内核无内置权限弹窗；用 `beforeToolCall` 钩子（Extension 层）自行实现权限门 |
| 凭证安全 | API Key 走环境变量 / CredentialStore；OAuth token 串行刷新；勿将密钥写入会话文件 |
| 遥测 | `PI_TELEMETRY` 环境变量控制 |
| 桌面端特有 | 渲染进程 `contextIsolation:true` + `nodeIntegration:false`；密钥只在主进程；高危操作必须经 `beforeToolCall` 审批门 |
