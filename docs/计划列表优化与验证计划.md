# 计划列表优化与验证计划

> 文档版本：1.0  
> 编写日期：2026-07-31  
> 适用范围：Pi Agent 自动执行模式中的计划生成、计划列表面板、任务索引持久化与 Agent 事件处理。

## 1. 目标

计划列表不再是独立的执行权限模式。用户在“自动执行”模式下明确要求计划，或系统识别到长线、多阶段任务时，Agent 必须先创建结构化计划，再自动调用工具逐项执行；计划创建成功后，界面自动展开计划列表。简单任务保持直接执行，不产生计划列表。

将计划列表从“根据模型文字和工具次数推断进度”的展示组件，升级为可验证、可恢复、可重规划的任务状态系统。

完成后应满足：

- 简单请求不产生计划列表。
- 复杂、多阶段任务可稳定生成计划草案。
- 每一项只能在有明确执行结果或验证证据时完成。
- 停止、报错、重启、上下文压缩后，计划进度保持准确。
- 计划变更可追溯，不会静默覆盖已完成工作。

## 2. 现状与必须修复的问题

当前实现会在任意成功工具调用后完成下一项，并且在一次 Agent 执行结束时完成其余所有项目。这两种“自动勾选”都会产生错误进度，必须删除。

| 问题 | 当前风险 | 修复原则 |
| --- | --- | --- |
| 工具调用成功即勾选下一项 | 工具与计划项没有必然对应关系 | 仅专用计划更新操作可改变状态 |
| Agent 结束即勾选全部剩余项 | 停止、失败、未验证任务被误报完成 | 只允许逐项完成 |
| 从自然语言猜测计划 | 模型格式不稳定时产生假计划 | 采用结构化计划数据 |
| 解析失败生成兜底计划 | 计划可能与用户任务无关 | 显示可重试状态，不虚构任务 |
| 新计划覆盖旧计划 | 无法查看重规划原因与历史 | 计划版本化并保留历史 |

## 3. 目标状态模型

### 3.1 计划生命周期

```text
draft -> awaiting_approval -> active -> completed
                                   -> cancelled
                                   -> superseded
```

### 3.2 单个计划项生命周期

```text
pending -> in_progress -> completed
                       -> blocked
                       -> skipped
```

约束：默认只能有一个 `in_progress` 项；支持并行任务时，必须显式标明该任务可并行。

### 3.3 建议数据结构

```json
{
  "id": "plan_20260731_001",
  "version": 1,
  "status": "active",
  "createdAt": "2026-07-31T12:00:00.000Z",
  "updatedAt": "2026-07-31T12:05:00.000Z",
  "sourceTurnId": "turn_xxx",
  "items": [
    {
      "id": "item_01",
      "text": "梳理现有会话持久化逻辑",
      "status": "in_progress",
      "dependsOn": [],
      "startedAt": "2026-07-31T12:01:00.000Z",
      "completedAt": null,
      "evidence": [],
      "toolCallIds": [],
      "turnIds": [],
      "blockedReason": null
    }
  ],
  "history": []
}
```

`evidence` 可以保存文件路径、测试命令和结果摘要、网页来源、产物路径或用户确认信息。没有证据时，任务不得标记为 `completed`。

## 4. 实施清单

### P0：准确性与数据安全（已完成：2026-07-31）

- [x] 删除“工具成功后自动勾选下一项”的逻辑。
- [x] 删除“Agent 结束时自动勾选全部剩余项”的逻辑。
- [x] 将 `{ text, done }` 迁移为完整的计划项状态模型，并兼容读取旧任务记录。
- [x] 将完成数改为由 `completed`、`skipped`、总项目实时计算。
- [x] 计划记录包含版本号和更新时间，并复用任务索引串行写入队列保存。
- [x] 停止任务时将当前执行项设为 `blocked`，不能设为完成。

验收：创建 7 项计划，仅完成 3 项后停止，重新打开任务仍显示 `3/7`；没有一个未执行项被勾选。

### P1：结构化计划更新（已完成：2026-07-31）

- [x] 新增内部计划工具：`plan_create`、`plan_update(start|complete|block|skip)`、`plan_replan`。
- [x] 模型通过结构化工具事件更新状态，而不是由前端扫描普通回复、工具次数或关键字。
- [x] `plan_update(action=complete)` 必须提供至少一条证据；没有证据会被工具拒绝。
- [x] 保留用户可读的计划列表，同时保存内部 JSON 状态；两者不互相覆盖。
- [x] 不再从普通回复创建计划，也不再生成通用兜底计划；历史对话中的旧包络仅作隐藏兼容处理。
- [x] 自动执行模式使用同一复杂度判断；仅长线、多阶段任务会先创建计划，再自动逐项执行。

验收：模型虽然调用了多个工具，但没有调用 `complete_plan_item` 时，面板状态不变化；有证据的单项完成后才增加完成数。

### P2：生成门槛与审批

- [ ] 新增任务复杂度评估：独立阶段数、文件/模块范围、依赖关系、预计工具步骤、验证要求、是否有不确定项。
- [ ] 简单问答、翻译、单文件小改、短命令、解释类任务默认不生成计划。
- [ ] 用户明确要求“先计划”时，始终生成草案。
- [ ] 对系统识别出的复杂任务，显示“建议先建立计划”，由用户确认后进入执行。
- [ ] 计划生成前允许只读研究项目结构；计划阶段禁止写文件和执行破坏性命令。
- [ ] 草案应包含实施步骤、验证步骤、依赖项和待确认问题。

验收：小任务连续测试 20 次不弹出计划列表；跨多个文件的功能任务能先显示草案，并在确认后开始执行。

### P3：执行、阻塞与重规划

- [ ] 开始工作前必须调用 `start_plan_item`，使当前工作项明确可见。
- [ ] 工具报错、缺少权限、用户中断或前置依赖失败时，调用 `block_plan_item` 并记录原因。
- [ ] 需求变化或发现新约束时调用 `replan`，保留已完成项，标记废弃项为 `superseded` 或 `skipped`。
- [ ] 每一次重规划产生新版本，并记录变更原因、时间和来源轮次。
- [ ] 支持用户在面板中手动重试、跳过、编辑或重新排序未完成项。

验收：完成两项后改变需求，原两项仍保留完成状态；新增和废弃项都有明确原因，进度不会归零或全部勾选。

### P4：面板体验与上下文恢复

- [ ] 顶部显示 `已完成/总数`、进行中数量、阻塞数量与最后更新时间。
- [ ] 项目状态使用统一图标：等待、进行中、完成、阻塞、跳过。
- [ ] 每项支持展开查看证据、关联工具调用与失败原因。
- [ ] 当前计划在任务结束后保留；下一个计划创建后才在主面板切换，历史版本可查看。
- [ ] 上下文压缩时保留计划摘要、当前项、未完成项与关键证据。
- [ ] 恢复历史任务时校验计划与会话轮次关联，丢失关联时给出“需要重新确认”的提示。

验收：压缩上下文、切换任务、关闭并重启软件后，计划状态和已完成数完全一致。

## 5. UI 文案与交互标准

| 状态 | 展示文案 | 用户可用操作 |
| --- | --- | --- |
| `pending` | 等待执行 | 编辑、跳过、调整顺序 |
| `in_progress` | 正在执行 | 停止、查看当前动作 |
| `completed` | 已完成 | 查看证据 |
| `blocked` | 已阻塞 | 重试、跳过、重新规划 |
| `skipped` | 已跳过 | 恢复、查看原因 |

完成进度采用：`完成 3/7 · 1 项进行中 · 1 项阻塞`。只有全部非跳过项均完成时，计划才显示“计划已完成”。

## 7. 建议的实施顺序

1. 完成 P0，先消除误勾选和错误计数。
2. 完成 P1，让计划生成和状态更新走结构化通道。
3. 完成 P2，降低误触发并加入计划确认。
4. 完成 P3，支持中断、失败和重规划。
5. 完成 P4，完善面板、历史和上下文恢复。
6. 按第 6 节逐项回归，全部通过后再打包发布。

## 8. 本次完成记录

### P0

- 计划项现在使用 `pending`、`in_progress`、`completed`、`blocked`、`skipped` 状态，并保存开始时间、完成时间、证据、关联工具调用和会话轮次字段。
- 旧版 `{ text, done }` 记录会在加载任务索引时迁移，不会丢失历史计划。
- 完成数从状态实时计算；工具调用成功和 `agent_end` 都不会自动勾选计划项。
- 用户点击停止时，当前执行项会标记为阻塞；计划事件带会话文件校验，避免串写到其他任务。

### P1

- 新增 `app/main/plan-tools.js`，提供 `plan_create`、`plan_update` 和 `plan_replan` 内部工具。
- 新增 `agent:planUpdate` 预加载事件通道，由渲染进程统一校验、更新和持久化计划状态。
- 计划工具调用不会显示为普通工具卡片，计划列表只展示用户可读状态。
- 完成操作必须携带验证证据；阻塞和跳过操作必须携带原因。
- 自动执行模式被判定为长线任务时，模型必须先创建计划，随后才可调用实现工具，并须逐项更新进度。

### 验证结果

- `node --check`：主进程、计划工具、渲染进程和预加载脚本均通过。
- `npm test`：10 项测试全部通过，其中 3 项覆盖计划创建、证据校验和重新规划。
- 源码 Electron 烟雾测试：使用独立临时用户数据目录启动后持续运行 12 秒，无主进程、渲染进程或计划列表相关错误；测试实例随后已关闭。
- 静态链路复核：计划工具已注册到每个 Agent 会话；内部计划工具在计划模式下允许调用；普通工具成功和 `agent_end` 均不再写入计划状态。
- 待人工连通性验证：使用已配置模型发送一次复杂任务，确认模型实际依次调用 `plan_create`、`plan_update(start)`、`plan_update(complete)`。隔离烟雾测试不复用正式 API 配置，因此不执行真实模型调用。
