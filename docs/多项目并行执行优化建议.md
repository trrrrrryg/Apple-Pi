# 多项目并行执行优化建议

> 文档版本：1.0  
> 编写日期：2026-07-31  
> 适用范围：苹果Pi 桌面端的项目、任务、Pi 会话、工具执行与改动审查。

## 1. 结论

可以支持同时运行多个项目，也应当支持。但不能只解除侧边栏的切换限制。

当前应用的主进程只有一个 `AgentService.session` 和一个 `_activePrompt`。每次切换对话时，`createSession()` 会释放当前订阅并重新打开另一个会话。因此它适合“一个任务运行、其他任务只读查看”，不适合两个任务同时调用模型、终端或写入文件。

已经实现的后台查看能力解决了“任务运行时不能查看其他对话”的问题：原任务继续运行，用户可浏览其他任务的历史，流式事件不会串到其他对话。下一阶段若要真正并发执行，需要把每个任务变成独立的运行单元。

## 3. 目标架构

每个任务应拥有独立的 `TaskRuntime`，而不是共享一个全局 Agent 会话。

```text
项目
  ├─ 任务 A ─ TaskRuntime A ─ Pi session A ─ 事件流 A ─ 工作目录 A
  ├─ 任务 B ─ TaskRuntime B ─ Pi session B ─ 事件流 B ─ 工作目录 B
  └─ 任务 C ─ TaskRuntime C ─ Pi session C ─ 事件流 C ─ 工作目录 C

TaskScheduler
  ├─ 全局并发限制
  ├─ 模型/厂商并发限制
  ├─ 终端并发限制
  ├─ 排队、取消与重试
  └─ 权限请求路由
```

`TaskRuntime` 最少应包含：任务 ID、Pi session、sessionFile、cwd、AbortController、运行状态、当前工具调用、上下文统计、计划状态、事件订阅取消函数、启动时间和最后活跃时间。

所有 IPC 需要显式携带 `taskId`。例如 `agent:prompt`、`agent:abort`、`agent:getState`、`agent:getHistory`、工具审批、计划更新和错误事件都应按任务路由，不能再默认指向“当前会话”。

## 4. 执行与隔离策略

### 4.1 不同项目

不同项目可默认并发，因为其 `cwd` 不同。仍需限制模型请求和终端进程数量，避免 API 限流、内存占用过高或多个终端任务耗尽系统资源。

建议默认值：最多 3 个运行任务；同一模型或厂商最多 2 个生成请求；同一项目最多 1 个写入任务。用户可在设置中将全局上限调整为 1 到 5。

### 4.2 同一项目的只读任务

搜索代码、联网研究、审查、生成计划、运行不修改文件的测试可以并行，并共享项目根目录。工具层应标记读写属性；只读任务不能执行写文件、安装依赖、Git 变更或破坏性终端命令。

### 4.3 同一项目的写入任务

禁止两个写入任务直接共享同一个工作目录。推荐策略如下。

| 项目状态 | 默认策略 | 原因 |
| --- | --- | --- |
| Git 仓库 | 为每个写入任务创建 Git worktree 与任务分支 | 文件、索引和分支隔离，可单独审查和合并。 |
| 非 Git 文件夹 | 默认排队；只有用户显式确认后才允许共享目录写入 | 缺少可靠的冲突检测、回滚与合并基础。 |
| 只读任务 | 可并行使用项目根目录 | 不产生文件覆盖风险。 |

worktree 命名建议：`.apple-pi/worktrees/<task-id>`，分支建议：`apple-pi/<task-id>`。完成、取消或审查拒绝后，应用只在用户确认或合并完成后清理 worktree，绝不自动删除未审查修改。

## 5. 用户界面建议

侧边栏任务项应同时展示状态和执行位置：`排队中`、`运行中`、`等待确认`、`已完成`、`失败`、`已取消`。运行中的圆点保持闪烁；排队任务显示顺序；等待确认显示醒目的权限标记。

切换任务应始终可用。正在运行的任务在后台继续，当前任务只控制自己的输入框和停止按钮。全局任务面板可提供“停止全部”“仅显示运行中”“按项目筛选”和“并发上限”操作。

同一项目的 worktree 任务需要在任务详情中显示“隔离工作区”和目标分支。任务完成后进入改动审查队列，用户可比较 Diff、接受、拒绝、重新运行或合并回项目主工作区。

## 6. 分阶段实施计划

### P0：稳定的后台查看，已完成

- 运行中的任务可以切换到其他任务查看历史。
- 原任务的流式文本、工具卡片、计划和完成状态不会串写到当前查看任务。
- 原任务结束后，当前查看任务自动恢复为可交互会话。

验收：任务 A 运行时切换到任务 B；B 的历史正常显示，A 继续输出；A 完成后 B 可以立即发送消息；A 的工具和计划更新不出现在 B 中。

### P1：多运行时与调度器

- 将 `AgentService.session` 改为 `Map<taskId, TaskRuntime>`。
- 所有 IPC 增加 `taskId`；事件、状态、审批和错误按任务发送。
- 新增 `TaskScheduler`，实现全局、厂商、模型和项目级并发限制。
- 支持排队、取消单个任务、取消全部任务、应用重启后的运行中任务恢复为已暂停。

验收：两个不同项目可同时执行模型回复和工具调用；停止 A 不影响 B；A 与 B 的上下文统计、计划列表、审批弹窗和完成通知均准确归属。

### P2：同项目冲突控制

- 识别 Git 仓库并提供“主目录只读 / 新建 worktree 执行”选择。
- 同项目最多一个共享目录写入任务；其他写入任务自动创建 worktree 或进入队列。
- 非 Git 项目默认不允许并发写入，并在任务界面说明原因。
- 为 worktree 记录源分支、任务分支、目录、创建时间和清理状态。

验收：同一仓库启动两个写入任务时，两个任务在独立分支和目录内完成；审查界面可分别查看 Diff；删除一个任务不会影响另一个任务或主目录。

### P3：审查与资源治理

- 任务完成后自动进入项目级审查队列，不直接修改主工作区。
- 提供合并前检查：未提交改动、冲突、测试状态和文件重叠检测。
- 设置中提供并发上限、后台任务通知、自动暂停阈值、最大终端数和最大内存提示。
- 记录运行耗时、token、工具次数、失败原因和重试次数，便于定位异常消耗。

验收：四个独立项目任务在设定并发上限内排队运行；超过上限的任务不会丢失；失败任务可重试；用户能在一个面板中看到资源与审查状态。

## 7. 风险与约束

| 风险 | 处理原则 |
| --- | --- |
| 模型限流与成本骤增 | 默认低并发，按厂商与模型做独立令牌桶/队列；在任务详情显示排队原因。 |
| 同一文件被覆盖 | 同项目写入必须 worktree 隔离或串行；禁止以“最后一次写入为准”处理冲突。 |
| 终端命令互相干扰 | 每个任务使用独立子进程、cwd、环境变量快照和 AbortController。 |
| MCP 服务不支持并发 | 为每个 MCP 声明并发能力；未知时按单实例串行，并将健康状态展示给用户。 |
| 应用退出或崩溃 | 启动时把未完成任务恢复为“已暂停”，保留会话、计划、日志和 worktree，不自动继续执行。 |
| 凭据泄露 | API Key 继续只保留主进程；任务事件、日志和导出内容须过滤密钥、Cookie、Authorization 头。 |

## 8. 推荐的下一步

先实施 P1，但第一版只允许“不同项目并发”和“同一项目只读并发”。这能以较小风险获得真正的多项目后台运行能力。P2 的 Git worktree 隔离应在 P1 稳定后实施，再开放同项目多写入任务。

在 P1 完成前，不应声称应用支持“多个项目同时执行”。目前正确的能力表述是：一个任务可以运行，其他任务可以随时切换查看；运行结束后立即恢复交互。
